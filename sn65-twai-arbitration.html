CAN Bus Arbitration Test — SN65HVD230/TWAI Migration

From SPI-Based MCP2515 to ESP32-C6's Native TWAI Controller

Author: Bahadir Batca  ·  Date: August 2026  ·  Version: v1.0

Embedded Systems CAN Bus TWAI Reproducible
Abstract

This report documents the migration of a two-node CAN bus arbitration test bed from an SPI-attached MCP2515 controller to the ESP32-C6's native TWAI peripheral paired with a standalone SN65HVD230 transceiver. The migration removes an external SPI link and a voltage level shifter entirely, exposes hardware-tracked arbitration statistics through the ESP-IDF driver API, and — critically — enables direct, per-node probing of each transceiver's digital TX line. A subtle software bug in which asynchronous transmit-queue processing caused arbitration events to be logged against the wrong transmission attempt is identified, diagnosed by cross-referencing software logs against a logic-analyzer capture, and corrected. The corrected setup is then used to capture, for the first time in this project, a direct, bit-level, per-node view of the exact bit at which the lower-priority node releases the bus during arbitration — something the bus-level (CAN-L) signal alone cannot show.

1. Background: Why We Migrated

The original test setup used an MCP2515 CAN controller (with an integrated TJA1050 transceiver module) driven over SPI through a TXS0108E level shifter. That setup successfully demonstrated CAN bus arbitration in software (via the controller's MLOA status bit and the driver library's return codes), consistent with the non-destructive arbitration mechanism defined in ISO 11898-1 [1]. However, it had two persistent limitations:

  • Occasional corrupted register/ID reads, eventually traced to a subtle SPI clock interaction with the TXS0108E level shifter.
  • No way to visually confirm, at the physical signal level, which side actually backed off during arbitration. The composite CAN-L bus line only ever shows the "winning" bit pattern — it cannot show which node released the bus.

To address the second limitation, the test bed was rebuilt around the SN65HVD230 [2], a standalone 3.3 V CAN transceiver with no built-in controller. This required moving the CAN controller logic itself onto the ESP32-C6, using its native TWAI (Two-Wire Automotive Interface) peripheral [3] instead of an external SPI-attached chip.

2. Hardware: SN65HVD230 Wiring

Because the SN65HVD230 operates natively at 3.3 V — matching the ESP32-C6 — no level shifter is required, and because the CAN controller is now built into the MCU, no SPI bus is required either. The wiring collapses to two digital signal lines per board, summarized in Table 1.

Removed entirely relative to the previous setup: the TXS0108E level shifter, the SPI wiring (previously GPIO7/6/2/10), and the autowp-mcp2515 library dependency.

3. Software Architecture: ESP-IDF TWAI Driver

The firmware structure (shared physical trigger, adjustable pre-send delay, burst transmission, sequence numbers for retry detection) was preserved from the MCP2515-based version. What changed is the CAN layer itself, now built directly on driver/twai.h [3]:

  • twai_driver_install() / twai_start() replace the MCP2515 library's reset()/setBitrate()/setNormalMode() calls.
  • twai_transmit() replaces sendMessage().
  • twai_receive() replaces readMessage().
  • TWAI_ALERT_ARB_LOST, read via twai_read_alerts(), replaces the manual SPI read of the MCP2515's TXB0CTRL register and its MLOA bit.
  • twai_status_info_t.arb_lost_count — a native, hardware-tracked cumulative counter — replaces the difference-based tracking previously built around the MCP2515's TEC register.

Since the CAN controller now resides in the same chip as the application code, rather than behind an external SPI link, the SPI clock/level-shifter interaction identified as a root cause in the prior phase of this project no longer applies, and diagnostic data is exposed through a documented driver API instead of raw register reads.

4. A Subtle Bug: Alert Misattribution

twai_transmit() only enqueues a message; it does not block until the message has actually completed transmission on the bus. Calling twai_read_alerts() immediately afterward, with only a short timeout, could occasionally return an alert belonging to a different queued message than the one just sent, since the hardware processes the TX queue asynchronously relative to the calling code. This produced a measurable, reproducible mismatch: cross-checking the software log against a direct probe on SLAVE's own TWAI TX pin (channel D3 in Figure 1) showed the logged arbitration-loss event attributed to burst index #25.3, while the actual physical bit drop-out on D3 occurred one attempt earlier, at #25.2.

Figure 1. The attribution mismatch: channel D3 shows the physical drop-out occurring during the second (25.2) transmission attempt, while the software log attributed the corresponding arbitration-loss flag to the third (25.3) attempt.

Fix. After calling twai_transmit(), the firmware now polls twai_read_alerts() in a loop, accumulating the returned flags, until twai_status_info_t.msgs_to_tx returns to zero — i.e. until the specific message just sent has fully left the transmit queue, however many retransmission attempts that required. Only then are the accumulated alert flags logged, guaranteeing that each log line's ARBLOST/TXFAILED fields describe the message that was actually just sent rather than a neighboring one:

esp_err_t res = twai_transmit(&frame, pdMS_TO_TICKS(50));

uint32_t alerts = 0, accumulatedAlerts = 0;
twai_status_info_t status;
uint32_t waitStart = micros();
do {
  twai_read_alerts(&alerts, pdMS_TO_TICKS(5));
  accumulatedAlerts |= alerts;
  twai_get_status_info(&status);
} while (status.msgs_to_tx > 0 && (uint32_t)(micros() - waitStart) < 20000);

bool arbLost  = accumulatedAlerts & TWAI_ALERT_ARB_LOST;
bool txFailed = accumulatedAlerts & TWAI_ALERT_TX_FAILED;

A repeat test after applying this fix confirmed correct attribution: the physical drop-out and the logged ARBLOST=1 line lined up on the same burst index (#37.1), and the corrected DUR measurement (≈486µs) now correctly reflected the real bus transmission time — including the back-off and automatic retry — instead of the near-instantaneous queue-enqueue time (11–23µs) that the unfixed code had been measuring.

5. Result: Arbitration Observed at the Bit Level

Direct, per-node probing of the transceiver's digital TX line was the original motivation for adopting the SN65HVD230. With a standalone transceiver, each board's own TWAI TX pin — a pure digital logic-level signal, prior to the transceiver — can be probed independently of the composite CAN bus line. Figures 2–4 show the result: the single bit at which SLAVE releases the bus is directly and repeatably visible, distinct from the merged bus signal.

Channel D3 in the following figures is SLAVE's own TWAI TX pin. Throughout the frame it toggles in its normal 0/1 pattern; at the exact bit where arbitration is lost, it shows a single, isolated anomaly — SLAVE stops actively driving that bit and goes recessive, because it detected a dominant bit on the bus where it was attempting to transmit a recessive one, consistent with the bit-wise, non-destructive arbitration mechanism of ISO 11898-1 [1].

Figure 2. Zoomed view of MASTER's winning frame (identifier 0x123). D3 (SLAVE's own TX pin) shows a single isolated dip within the identifier field — the exact bit at which SLAVE backs off, distinct from its otherwise regular toggling.

Figure 3. A wider view spanning the frame boundary. D3 shows the single arbitration-loss anomaly during MASTER's frame (0x123), then resumes full, healthy toggling once SLAVE's own frame (identifier 0x456) begins immediately after.

Figure 4. Two separate arbitration events captured back to back. In both instances the same signature appears on D3 — a single anomalous bit at the start of the identifier field — indicating a consistent, reproducible signal rather than a one-off artifact.

This directly confirms the hypothesis raised at the end of the MCP2515-based phase of this project: the inability to observe the back-off on CAN-L alone was never a resolution or measurement-bandwidth issue — CAN-L is inherently a composite of both nodes' signals during arbitration. Only a per-node, pre-transceiver probe point, made practical here by the SN65HVD230's exposed digital TX pin, can reveal which node released the bus.

6. Limitations

  • The test bed consists of exactly two nodes on a single physical bus segment; the observed arbitration behavior has not been validated with three or more competing nodes, where multiple simultaneous back-offs could occur.
  • All tests were run at a single fixed bitrate (500 kbps, standard 11-bit identifiers). Behavior at other bitrates, with extended (29-bit) identifiers, or under CAN FD framing was not evaluated.
  • The fixed fault-injection mechanism is a shared physical push-button combined with a software-adjustable pre-send delay; it induces near-simultaneous transmission attempts but does not allow deterministic, cycle-accurate control over the exact timing offset between the two nodes.
  • Bus loading was minimal (two nodes, low duty cycle); behavior under sustained high bus utilization was not characterized.

7. Future Work

  • Extend the test bed to three or more nodes to observe multi-way arbitration and confirm that back-off ordering remains consistent with identifier priority across more than two competing frames.
  • Repeat the bit-level capture at additional bitrates (e.g. 125 kbps, 1 Mbps) and with CAN FD framing to check whether the single-bit signature on the TX pin remains equally clear at different bit timings.
  • Replace the manual/software-timed trigger with a dedicated, cycle-accurate pulse generator to sweep the inter-node timing offset deterministically and map the full transition boundary between "no collision" and "arbitration occurs."
  • Introduce controlled bus-level fault injection (e.g. a third node forcing dominant bits) to study arbitration behavior under adversarial conditions rather than only cooperative, well-behaved nodes.

8. Reproducibility

All firmware (MASTER/SLAVE), the platformio.ini build configuration, and the raw logic-analyzer captures referenced in this report are intended to accompany this document in the same repository. To reproduce these results:

  1. Build two identical ESP32-C6 nodes wired per Table 1, sharing a single CAN bus with 120Ω termination at both ends and a common physical trigger line (GPIO3) with local debounce capacitance.
  2. Flash the master and slave firmware environments to the respective boards via PlatformIO (pio run -e master -t upload, pio run -e slave -t upload).
  3. Trigger the shared button and observe the serial output on both boards (115200 baud) for ARBLOST/dARBLOST events.
  4. For bit-level confirmation, probe each board's TWAI TX pin (GPIO0) individually alongside the CAN bus line with a logic analyzer sampling at ≥2 MHz.

9. Conclusion

  • The test bed was successfully rebuilt around the SN65HVD230 transceiver and the ESP32-C6's native TWAI controller, eliminating the SPI bus, the MCP2515 library, and the TXS0108E level shifter entirely.
  • A subtle alert-attribution bug, caused by twai_transmit()'s asynchronous queuing behavior, was identified by cross-checking software logs against a direct pin-level capture, and corrected by waiting for msgs_to_tx == 0 before logging a result.
  • The original goal of this hardware migration was achieved: the single bit at which the losing node (SLAVE) backs off during arbitration is now directly and repeatably observable on that node's own TWAI TX pin — a view that was not obtainable with the previous MCP2515 + TJA1050 configuration.
